# Эксплуатация технического центра

## Конфигурация и установка

Изменения БД аддитивны в `backend/sql/schema.sql`; entrypoint применяет их штатным способом. API и worker используют один образ с `APP_RELEASE`, переданным через build argument `DOMLY_RELEASE_SHA`. Статические файлы панели входят в образ. Firebase для технического Web Push не используется; FCM приложения остаётся без изменения.

Production развёртывается только проверенным commit из main через штатный GitHub Actions Deploy. Скрипт **до переключения** сохраняет PostgreSQL и backend.env в защищённом каталоге `backups/<timestamp>-<sha>/`. Конфигурация Compose (версия, пути мониторинга и плановых копий) сохраняется в серверном `.env`, чтобы последующие служебные workflow не теряли mounts.

Первую инициализацию запускает workflow **Initialize technical panel** с mode=initialize. Для повторной read-only проверки используйте mode=inspect: он не пересоздаёт учётные записи, не меняет ключи и не перезапускает сервисы. На рабочей машине получателя:

```sh
umask 077
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out technical-recipient.pem
openssl pkey -in technical-recipient.pem -pubout -out technical-recipient.pub
base64 -w0 technical-recipient.pub
```

Передайте workflow только base64 **публичного** ключа. Он создаёт на сервере `TECH_AUDIT_KEY`, VAPID-пару, закрытый бакет для отклонений и отдельного владельца. Начальный пароль возвращается только RSA-OAEP-SHA256 шифротекстом. Расшифруйте у получателя, храните файл доступа вне репозитория; после первого входа смените временный пароль. Не публикуйте расшифрованный JSON в Issues, workflow logs или статическом хостинге. Приватный ключ никогда не передаётся серверу/Actions. Повторная инициализация не сбрасывает существующего владельца.

Необходимые значения, только в защищённом backend.env:

- `TECH_AUDIT_KEY` — неизменный ключ HMAC; потеря делает старые подписи непроверяемыми. Не заменять без отдельного плана смены и сохранения старого ключа.
- `TECH_VAPID_PUBLIC_KEY` / `TECH_VAPID_PRIVATE_KEY` — пара для браузерного push; приватная никогда не выдаётся UI.
- `TECH_PRIVATE_BUCKET=domly-technical-private`.
- необязательный `TECH_STATUS_FILE`, по умолчанию `/run/domly-status/status.json`.

Инициализация устанавливает `/etc/cron.d/domly-technical-status`; агент `shared/technical_status.py` выполняет только фиксированные read-only probes, подписывает JSON в `shared/technical-status/`. API/worker получают этот каталог read-only. Если агент перестал работать, панель показывает устаревание, а не успех.

## Резервные копии

Плановый backup сохраняет PostgreSQL, основной бакет MinIO и отдельно закрытый технический бакет с SHA-256. Путь стабилен между релизами: `backups/scheduled`. Для закрытого бакета создаются `technical/technical_<timestamp>.tar.gz` и файл `.sha256`. Успешная manifest-запись появляется после выполнения операций. Не считайте один SQL-дамп полной копией: нужны объекты, защищённая конфигурация с HMAC/VAPID, а также checkpoint аудита. Начальная конфигурация backend.env и её резервные копии доступны только серверным администраторам.

Срок плановых backup-архивов — 14 дней. Deployment-backup имеет отдельный жизненный цикл и автоматически этим правилом не удаляется. Копии находятся на том же VPS: **это не защита от полной потери сервера**. Для такой защиты нужно отдельно настроить зашифрованное внешнее хранилище и проверить восстановление оттуда.

## Восстановление

Выполняет серверный администратор через защищённый SSH, не через браузерную SQL-консоль:

1. Остановить api/worker и сделать копию текущего повреждённого состояния для расследования.
2. Выбрать согласованный timestamp SQL, основного и технического бакетов. Проверить SHA-256. Развернуть новую чистую PostgreSQL, MinIO и изолированную сеть; не вливать полный dump в заполненную БД.
3. Восстановить SQL через `gunzip -c <dump> | psql ... -v ON_ERROR_STOP=1` (или plain `postgres.sql` штатного deploy-backup).
4. Запустить `backend/backup/restore.sh` с точными путями и SHA, `RESTORE_CONFIRM=YES`; для закрытого бакета дополнительно `TECHNICAL_RESTORE_ENABLED=true`, `TECHNICAL_BACKUP`, `TECHNICAL_BACKUP_SHA256`. Проверить, что выбран ожидаемый бакет и в нём нет публичной политики.
5. Восстановить соответствующий backend.env (HMAC/VAPID особенно важны), а не генерировать новые ключи. Вернуть согласованный root-checkpoint аудита; сверить его с архивами.
6. Проверить в изолированной среде число пользователей/объектов, вход владельца, цепочку аудита, контрольные суммы нескольких оригиналов, отказы доступа, очередь и `/ready`.
7. Только после этого переключить production, проверить фактический APP_RELEASE и все три приложения. Не отправлять реальные сообщения/платежи при тестовом восстановлении: отключить соответствующие интеграции и фоновые отправки.

При потере только пароля владельца: уполномоченный серверный администратор после резервной копии создаёт новый случайный пароль bcrypt cost 12 в `tech_accounts`, выставляет `must_change_password=TRUE`, отзывает `tech_sessions`, фиксирует инцидент в защищённом аудите. Существующий пароль расшифровать нельзя. Браузер не предоставляет произвольный SQL и не может менять владельца. Локальный encrypted-конверт первого запуска полезен только до первой смены пароля.

## Хранение и доказательства

По умолчанию события хранятся 30 дней, карантинные оригиналы — 14, горячий аудит — 365. Пороги версионируются. Очистка worker идёт ограниченными порциями; при недоступном MinIO запись не помечается удалённой без успешного удаления. После удаления оригинала карточка прямо говорит об этом. Метаданные удалённых карантинных файлов без события очищаются через 90 дней. Основные бизнес-документы подчиняются отдельной политике приложения; техническая очистка их не удаляет.

Аудит append-only с HMAC-цепочкой и запретом UPDATE/DELETE обычным путём; разрешённая очистка сначала сохраняет gzip NDJSON в закрытый бакет с границами цепочки и SHA-256. Горячая проверка охватывает последние 1000–2000 записей, архивы перечислены отдельно. Root-агент хранит отдельный checkpoint вне БД. Это обнаружение изменений в обозначенной области, **не гарантия против компрометации root, приложения и ключа одновременно**. Отдельного внешнего WORM-хранилища здесь нет. Архивы нельзя незаметно считать проверенными только по наличию строки метаданных: при восстановлении проверяют содержимое/контрольные суммы и ключи.

SQL имеет 30-секундный server-side statement timeout, соединение ограничено пятью секундами. Списки имеют лимит 100 и максимум 10 000 страниц. Файлы до 50 МБ/40 Мп. Вход ограничен десятью неудачными попытками за 15 минут по логину или хешу IP. Клиентские события — до 20 за запрос и 120 за минуту на аккаунт. Это защитные пределы, а не нагрузочная сертификация.

Ошибка коллектора увеличивает диагностический счётчик API/worker и пишет фиксированный безопасный marker. Когда БД недоступна, записать в неё событие невозможно; история после перезапуска может иметь пробел. Не заполнять его вымышленными операциями.

Полная потеря VPS останавливает и панель, и её push-worker. Для независимого оповещения об этом нужен отдельный внешний мониторинг; внутренний центр не изображает доставку при остановленном сервере.
