# DomLY — API оформления для MooonAI
## Статус и доступ
Версия документа 1.0. Подготовлено 13.11.2026. Методы доступны только после выкладки соответствующего backend и настройки отдельного MOON_AI_ORDERING_TOKEN. До проверки выкладки документ нельзя считать подтверждением работы production.
Базовый адрес: https://domly.kz/api/v1/integrations/moon-ai/ordering
В каждом запросе передавайте заголовок X-MoonAI-Ordering-Token. Это отдельный токен оформления; он не является токеном клиента, администратора или банковских уведомлений. Не отправляйте его клиенту, не помещайте в URL, публичные файлы или логи. При утечке замените MOON_AI_ORDERING_TOKEN на сервере.
У изменяющих методов /packages, /payments/verify, /orders обязателен Idempotency-Key: 8–128 символов из A–Z, a–z, цифр, _, ., :, -. Для повтора одной операции используйте тот же ключ и точно такое же JSON-тело. Для другой операции — новый ключ. При тайм-ауте повторяйте прежний запрос с прежним ключом.
Ответ успеха: {"ok":true,"data":...}. Ошибка: {"ok":false,"code":"...","message":"..."}. Телефон — +7XXXXXXXXXX. Все идентификаторы адресов, пакетов и оплат — UUID из ответов API.
## 1. Найти клиента
GET /customer?phone=%2B7XXXXXXXXXX
Возвращает addresses, packages, orders и qualityChecks. Адреса включают id, город, улицу, дом, квартиру и площадь; пакеты — id, статус и доступные уборки. Выбирайте только адреса и пакеты из ответа этого клиента.
404 customer_not_found означает, что активного зарегистрированного клиента нет. Предложите зарегистрироваться в приложении; этот API не создаёт клиентские аккаунты. Заблокированные и удалённые аккаунты исключены.
## 2. Каталог и точная цена
GET /catalog?area=67
Возвращает действующие тарифы, допуслуги, их цены и условия. consentVersion и features.importantInfo нужны для тарифа с обязательным согласием. Площадь в GET используется только для предварительной оценки.
POST /quote — без Idempotency-Key, но с токеном. Пример тела:
{"phone":"+7XXXXXXXXXX","packageId":"UUID_ТАРИФА","addressId":"UUID_АДРЕСА","cleaningsPerMonth":2,"addonsDetailed":[]}
Для окончательной цены используйте именно /quote: сервер берёт площадь адреса клиента и применяет его скидки. cleaningsPerMonth нужен для квартального тарифа: 2, 4 или 8. addonsDetailed: [{"id":"UUID_ДОПУСЛУГИ","quantity":1}]. Услуги с отдельной оплатой не включаются в счёт: их оплачивают специалистам по факту.
Сумма к оплате — monthlyPrice за весь пакет, не ежемесячный платёж. Количество визитов — cleaningCount. Цены, площадь, скидки и итог не принимаются на доверии от бота. Для уборки после ремонта допуслуги не выбираются.
## 3. Создать пакет и счёт
POST /packages + Idempotency-Key. Пример тела:
{"phone":"+7XXXXXXXXXX","packageId":"UUID_ТАРИФА","addressId":"UUID_АДРЕСА","cleaningsPerMonth":2,"addonsDetailed":[],"provider":"kaspi","confirmedByCustomer":true}
До запроса покажите клиенту тариф, адрес, услуги, цену и получите согласие. Если тариф требует прочитать важную информацию, добавьте acceptedTermsVersion из consentVersion актуального каталога. Если условия изменились — покажите новые и получите согласие повторно.
Сервер создаёт customerPackage со статусом pending_payment и payment, затем инициирует счёт. Для Kaspi счёт отправляется существующей интеграцией MooonAI на зарегистрированный номер клиента. API не принимает другой номер плательщика, произвольную цену или команду «считать оплаченным».
В ответе сохраните customerPackage.id и payment.id. Наличие пакета и успешный HTTP-ответ ещё не означают, что клиент заплатил. Статус invoice_requested означает постановку отправки счёта, а не оплату.
provider=bcc поддерживается для платёжной формы BCC: payment.payload содержит paymentHtml/actionUrl/providerPayload. Форму должен открывать доверенный интерфейс; её нельзя выдавать за обычную готовую ссылку оплаты. Данные карты вводятся только у банка. Основной сценарий бота в этом документе — выставление счёта Kaspi.
Бонусы этим API не списываются. Повтор с тем же ключом возвращает тот же пакет и платёж, не создавая второй счёт. При неизвестном результате доставки счёта не создавайте новый платёж автоматически: требуется проверка поддержки.
## 4. Проверить оплату и активировать пакет
POST /payments/verify + Idempotency-Key. Пример тела:
{"phone":"+7XXXXXXXXXX","paymentId":"UUID_ПЛАТЕЖА"}
Ответ содержит payment.id/status/provider, customerPackage.id/status/available_cleanings, readyToBook и source. Продолжайте бронирование только при readyToBook=true.
Для Kaspi API читает состояние, подтверждённое существующим защищённым платёжным callback. Этот метод не опрашивает Kaspi напрямую и не заменяет подтверждение платёжного сервиса. При pending/invoice_requested дождитесь callback. Для BCC сервер проверяет платёж запросом в банк, проверяя сумму, валюту и принадлежность операции. Тестовый BCC-платёж не активирует пакет.
Поля paid:true, status:paid, скриншот чека или текст сообщения клиента не подтверждают оплату. Активация выполняется сервером однократно после достоверного оплаченного статуса. Чужой paymentId не принимается.
Каждая новая проверка после ожидания — новый Idempotency-Key: повтор прежнего ключа вернёт результат прежней проверки, в том числе pending. Не опрашивайте чаще одного раза в 15 секунд; при длительном ожидании предложите поддержку. Не создавайте новый пакет вместо ожидающего оплаты без согласия клиента.
## 5. Получить доступное время
GET /slots?phone=%2B7XXXXXXXXXX&customerPackageId=UUID_ПАКЕТА&date=2026-12-01
Ответ — массив {startTime,endTime,durationMinutes,cleanersCount}. Если нужно передать допуслуги: addonsDetailed — URL-кодированная JSON-строка массива. Выбирайте дату, затем услуги, затем время.
Продолжительность и доступность рассчитывает сервер. Учитываются утверждённые графики, уже назначенные уборки и пересекающиеся заказы, ещё ожидающие исполнителя. Пустой массив означает, что доступного времени нет; предложите другую дату. Данные календаря предварительные — наличие места проверяется ещё раз при создании заказа.
Бронирование возможно с завтрашнего дня по времени Алматы. Начало 08:00–18:00 включительно; 18:05 нельзя, окончание после 21:00 допустимо. После ремонта — минимум за 24 часа, расчёт 25 мин/м². Стандартная уборка — 1,6 мин/м² плюс длительность услуг. Не рассчитывайте время самостоятельно.
## 6. Создать уборку
POST /orders + Idempotency-Key. Пример тела:
{"phone":"+7XXXXXXXXXX","customerPackageId":"UUID_ПАКЕТА","date":"2026-12-01","startTime":"18:00","addonsDetailed":[],"confirmedByCustomer":true}
Сначала получите согласие клиента на дату и время. Сервер проверит владельца и оплату пакета, срок действия, заморозку, доступный остаток, начало, длительность, пересечения клиента и наличие исполнителей. Проверка и списание визита происходят в транзакции; одновременные запросы сериализуются, незакреплённые заказы тоже занимают ёмкость. При неуспехе визит не списывается.
В ответе: order и offer. pending_assignment/waiting_cleaner — заказ создан, но исполнитель ещё должен принять предложение. Не обещайте клиенту подтверждённого исполнителя до assigned. Принятие заказа уборщицей отдельно защищено от пересечений. API не принуждает уборщицу принимать заказ.
Новые допуслуги, требующие доплаты, нужно оплатить в составе пакета до такого бронирования; иначе вернётся addons_payment_required. Отдельно оплачиваемые специалистам услуги счета не создают. После ремонта список допов запрещён.
Квартальные визиты можно использовать заранее в пределах оплаченного срока; помесячное сгорание неиспользованной квоты сохраняется. Окончательное решение об остатке и дате принимает сервер.
## Журнал в админке
Раздел «Аудит»: исполнитель «Бот MooonAI», действия bot.moon-ai.*. actor_id не подставляется от имени клиента. Записываются customerId, requestId, операция, время, result=success/error, код ошибки и признак повторного запроса replay.
Создание пакета и счёта, проверка оплаты, просмотр контекста/каталога/слотов, расчёт и создание заказа фиксируются. У пакета purchase_config и у созданного платежа payload есть createdBy=bot, bot=MooonAI, botRequestId. Для созданного заказа сохраняется отдельная запись с entity_type=order и его ID. Административное уведомление о покупке/заказе указывает, что его оформил бот.
Уже существующие методы бота для площади также отмечаются как действия бота. Уведомления об оплате от MooonAI отмечаются отдельно. Ошибочные запросы после успешной авторизации тоже фиксируются. Токены, реквизиты карт и полный текст диалога в аудит не записываются. Неавторизованный запрос не считается действием подтверждённого бота.
## Ошибки и повторы
400 — исправьте данные/согласие/дату. 401 — проверьте отдельный токен оформления. 402 payment_required — дождитесь оплаты. 404 — клиент или принадлежащий ему объект не найден. 409 idempotency_conflict — ключ уже использован с другим телом; не меняйте ключ для повторения неизвестного результата старой операции.
409 slot_unavailable/customer_booking_overlap — ничего не списано; снова получите слоты и согласуйте другой вариант. 409 package_terms_required — покажите текущие условия. 409 addons_payment_required — сначала оплатите допы. 503 — временная недоступность интеграции, повторяйте прежнюю операцию с прежним ключом после ожидания.
При ошибке сначала проверьте сохранённые пакеты/заказы и статус платежа. Не отправляйте человеку несколько счетов из-за сетевого тайм-аута. Один ключ должен сохраняться во внешней системе MooonAI вместе с операцией до окончательного результата.
## Проверка перед включением
Нужны выкладка backend, миграция таблицы bot_ordering_requests, отдельный секрет MOON_AI_ORDERING_TOKEN и проверка авторизованного запроса. Секрет не публикуется в GitHub. Закрытый PDF с реальным токеном выдаётся владельцу после настройки сервера; публичная документация содержит только описание заголовка.
Контрольный сценарий на тестовой базе: найденный и отсутствующий клиент; чужой адрес; одновременные повторы покупки; неподтверждённый платёж; попытка подставить paid; оплаченный пакет; последнее свободное время при двух одновременных заказах; пересечение клиента; поздний старт; запись в аудите и отсутствие повторного списания.
